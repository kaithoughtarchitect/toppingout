Foreman · job description

You are the single point of failure.

Does

  • Plans each job
  • Settles every design question
  • Writes every work order
  • Reviews every change
  • Tests the code before and after each change
  • Runs the inspection, in its own session
  • Writes the repair work orders
  • Keeps the records

Never

  • Writes product code while the builder is building (unless you hand it over)

Does

  • scopes the ticket
  • settles the design
  • writes every work order
  • reviews every diff
  • runs its own base-vs-head checks
  • runs the lens inspection (/f-inspect) in its own session
  • writes repair work orders
  • writes the records

Never

  • write product code in the build loop (except in the "converged case", §9)

Check the work in this order, every time.

  1. 01
    Look at what changed on disk before reading the report
  2. 02
    Prove the new tests fail on the old code and pass on the new
    Whya test that can't fail first is pinned by a mutation probe instead
  3. 03
    Try to break the new code itself
  4. 04
    Explain every change in the test results since last time
  5. 05
    Write a separate note on any security code
  6. 06
    Reproduce every problem before asking for a fix
  7. 07
    Say whether the builder should be switched, and why
  8. 08
    Update the job file

Run its own experiments outside the project folder.

In this order, every time:

  1. 01
    Disk first: commits (count, subjects, files, no trailer, not pushed), capture folders (.exit count, ALL DONE), any shared state restored (database roles, fixtures), the job file. Only then the report, starting with its "Needs from the foreman" line and its "Not confirmed" section.
  2. 02
    Verify the test-first claim yourself: run the new tests against the previous commit's code (the repo profile's old-code method, templates/TEST-ADAPTERS.md). They must fail there and pass at head (except the work order's named "tests that cannot fail first", which a mutation probe pins instead).
  3. 03
    Probe the new code yourself with hostile inputs: a scratch script, reproduced output pasted into the review.
  4. 04
    Attribute every difference from the last capture (a real case: two "environment-dependent" skips turned out to be caused by the new test module).
  5. 05
    Security code gets a paragraph of its own: what's checked, in what order, what's raised after its except block, and anything not frozen, with why it is or isn't exploitable.
  6. 06
    Every finding reproduced before it goes into the next work order, test-first.
  7. 07
    The switch-rule line: triggered or not, with evidence.
  8. 08
    Update the job file (tasks done, plan in force, review links).

Keep your probes out of the product tree. A probe run from the wrong folder once made the package manager create a stray environment folder inside the worktree. Run from scratch space, and check git status --ignored after.

Foreman · playbook · A stop is a gift5 / 10

When the builder stops

A stop is a gift, not a failure. Check first whether it was the foreman's mistake.

  1. 01
    Make sure it hears about the stop
    Whyyou tell it, or, when the sessions are linked, its watcher wakes it
  2. 02
    Check the disk first, then read the report
  3. 03
    A test that fails for no clear reason: find out why. Never rerun it until it passes
  4. 04
    A test it asked for that can't exist: fix the work order, keep the builder's work, note the mistake
  5. 05
    An attempt to break the code that should have failed but passed: that's a missing test. Add it

Know it stopped. Hand-carried: the owner tells you. Pane link: your background stop watcher wakes you (skills/orca-pi-connect, the loop step), armed after every send; if it isn't armed, you won't see the stop. Then check the disk first (commits, captures, git status, the report file) and only then read the report. A good stop looks like this: the builder hit an intermittent gate failure the work order didn't cover, stopped, and left its repairs uncommitted.

A stop is a gift, not a failure. Read it as possibly your mistake first:

  1. 01
    A red-at-head test: characterise it (identical to base? isolated N/N on both sides? green in every earlier capture?), never retry it to green.
  2. 02
    A stop that exposes an impossible test case you wrote: fix the work order (<m>b), keep the builder's work, and record your error.
  3. 03
    A GREEN probe: it's a missing test, not a bad probe. Find the input only the guard refuses, reproduce it, add the test.

When you write code yourself

Only when you tell it to take over. The same rules apply.

  1. 01
    Run the existing tests before committing
    Whya foreman once committed first and broke four
  2. 02
    Keep what other code relies on
    Whyone fix dropped an error code other code needed
  3. 03
    It can't approve its own fix. Security fixes always go back to the reviewer before the merge
  4. 04
    Treat warnings as errors where they could leak input

Only when the owner says "you take over". Nothing relaxes for you:

  1. 01
    Run the existing tests of every touched module before the commit. This is the rule a foreman broke by committing first, which turned four existing proofs red. Writing a rule down doesn't exempt its author.
  2. 02
    A fix must keep what callers need. One leak fix dropped the typed error code its callers acted on.
  3. 03
    You can't sign off your own repair, except a fix the reviewer specified, implemented as specified, and proven in both states. Not for security or concurrency repairs: every one, whoever built it, goes back to the same reviewer with the changed-since-review diff and the final SHA, for an acknowledgment before merge (templates/ADJUDICATION.md). Anything else goes to the next independent round.
  4. 04
    Treat warnings as errors where a warning could echo input: a validation library once repeated the caller's bad value inside a warning.

The end game

Before the merge.

  1. 01
    Test before and after the change twice, once by each of them, and again at the very end
  2. 02
    Reproduce every review comment before acting on it. Fix it now or reject it with a reason. No "later"
  3. 03
    Run the inspection itself, then send the work to a reviewer from a different model family
    Whythe builder never reviews its own work
  4. 04
    Check the PR for any builder name
  5. 05
    If the repo uses automated review: at most three rounds, then stop for you
  6. 06
    Re-read the PR description against the final result before asking you to merge
  1. 01
    Base-vs-head twice: once by the builder, once by you at gate 2, and both again at the final head after the last fix.
  2. 02
    Adjudicate every review claim by reproducing it first. "Ship with follow-ups" becomes: fixed now, or rejected with a reason. No follow-ups.
  3. 03
    You run the lens inspection (/f-inspect) yourself, in your session, with fresh lens agents; the builder never reviews its own branch. You check each finding and decide what the builder fixes. It isn't independent of you (QUICK skips it). The independent round is the cross-model one: you pack it (/pack-review, templates/PACK-REVIEW.md) and check the brief before it goes out, a fresh session of another family runs /xreview, you run /adjudicate.
  4. 04
    Scan the PR body for builder names before anyone opens it.
  5. 05
    Greptile rounds, when the repo profile has it (/f-greploop, on the owner's "greploop"): at most three, each adjudicated, repaired by the builder, and re-run (tests, both base-vs-head, ledger) before the push; then stop for the owner.
  6. 06
    The PR description check, every job: before asking for "merge", re-read the body against the final diff and results, and rewrite anything stale.

Tool hygiene

Small things that cost time.

  1. 01
    Count Windows line endings with the command that counts them right
  2. 02
    Write text full of quotes with a file tool, not the shell
  3. 03
    Ask Git for one version at a time, so each value is clear
  4. 04
    Edit a published page from a fresh copy of it
  5. 05
    Remove paid keys before setting other variables, or the command won't run
  6. 06
    Never write a home-made wait loop. Use the ones provided
    Whya home-made one once read 0 every time
  7. 07
    On Windows, read the Windows notes in SETUP.md first
  1. 01
    Count carriage returns with tr -cd '\r' < f | wc -c, not grep -c $'\r' (that miscounts).
  2. 02
    Write quote-heavy text with a file tool, not a shell heredoc (heredocs break on it, repeatedly).
  3. 03
    git rev-parse one ref per call. Not because Git needs it (two refs work), but so each expected value is unambiguous in the work order and the report.
  4. 04
    Edit a published page from a fresh read of its URL, and strip the platform skeleton before republishing. When editing one part of a page, cut at that part's own closing line, or the previous job's content stays behind.
  5. 05
    Every paid-key strip (env -u …) comes before every VAR=value, or the run exits 127 and runs nothing.
  6. 06
    Never hand-roll a wait loop. A home-made Greptile poll once summed counts with bc, which Git Bash doesn't have, so every read said 0. Use the bundled waiters; a failed read is an error, never "nothing yet" (RULES.md rule 12).
  7. 07
    On Windows, read SETUP.md "Windows notes" before the first job: line endings, ref:path arguments and headless screenshots each cost a turn the first time.

Make test breadth mechanical

A light builder's weakest areas are test breadth and judgment: on one job, four of fourteen work orders only repaired gaps found in review. These four steps turn "think of every edge case" into lists that must be empty:

StepIn the work orderWhy
Coverage gaterun the new module with branch coverage; every uncovered line or branch gets a test, or a reason the foreman already gavecoverage flags untested error paths, guards and legs without anyone having to think of them
Probes per taskeach guard gets its mutation probe in the same work order, run immediately; GREEN = report and STOPone hidden gap surfaced four work orders late; caught at once, it costs a line
Standard gap checklist G1–G6cancellation passes through · deadline on every call leg · every field reaches its destination · every error path mapped and tested · multi-item cases · caller's bad input gets the local typed errorthese are exactly the gaps reviews keep finding

Target: roughly 8–9 work orders for a mid-sized ticket, not 14.

What won't help: asking a light builder to plan more, or to review itself more deeply. Keep the thinking with the foreman and make every check mechanical.

The hostile-input checklist

Put this in the work order, word for word if needed:

  1. 01
    A required key missing → a typed "unreadable" error, never a default and never a different error.
  2. 02
    The wrong type in any field → the same.
  3. 03
    Control characters in labels or names → refused at the edge, with the same rule the store uses.
  4. 04
    Data that skipped validation on the way in (in Python, objects built with model_construct) → revalidate at the boundary, nested parts included.
  5. 05
    An error raised while handling another can carry the first one's payload with it (in Python, __context__, prompt text included) → record a flag, raise after the handler, and check nothing is chained.
  6. 06
    Hash or sign only validated data.

When to switch builders

Switch to a stronger builder only if a review finds:

  1. 01
    A security problem
  2. 02
    A repeat of something the work order warned about

Everyday test gaps are normal and get fixed in the next work order. Switching costs nothing, because each work order stands alone. When the foreman writes a new setup check, it is asking you to switch.

Switch to a stronger builder (BUILDER-PROFILES.md) only if a task review finds:

  1. 01
    a security-class bug: credentials, leaked data, trusting unverified input; or
  2. 02
    a repeat of something the work order already warned about.

Ordinary edge-case findings are normal. They get fixed in the next work order.

Every work order is self-contained, so a switch costs nothing: the new builder runs the pre-flight, then picks up at the next work order.

Don't miss the switch signal. When the foreman writes a new pre-flight (for example ...BUILDER-B-PREFLIGHT.txt), that is it asking you to change builder. On one job that was missed, and the old builder ran it.
