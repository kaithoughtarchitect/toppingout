# Changelog

What changed for a project that upgrades, newest first. `/f-setup` shows the entries your install hasn't seen yet. To upgrade: between jobs, run `/f-setup` in your project (see the README, "Updating").

## 2026-11-24

- **The pitch: you choose the builder.** The README, `AGENTS.md` and the site no longer say the builder is a cheaper model: the foreman runs on Opus or Fable, and the builder on whatever model you pick for each job, a frontier model, a fast one or a cheap one. The method is what makes any of them safe. "Try it" lists every required tool up front.

## 2026-11-23

- **An autonomous run or a night shift can take acts 8 and 9 on a standing grant.** The repo profile's new "Standing grant (acts 8 and 9)" row holds the owner's own words, quoted, or `none` (the default, and the old rule). With a grant, a run may edit a file the job needs outside its ticket's files (act 8) and add at most one new migration file pair per job (act 9), both only inside the board's entry for that job; the foreman quotes the row into the job file each time and lists every such file in the PR body and the dev report. It never applies a migration to a non-disposable database, goes beyond the job's board entry, touches a file another job owns, or does anything irreversible or reserved for the owner (`RULES.md`, "A standing grant for acts 8 and 9"). `/f-shift` quotes the row with the job's facts, and the night shift's pre-flight records it and says when a shift will need it but the row is `none`.
- **Gaffer's tests no longer fail at random on CI.** Run under `--test`, Node 22 reads the test file's output through a child process, and that reader can crash ("Unable to deserialize cloned data", nodejs/node#66164, fixed only in Node's main branch). It failed Ubuntu CI twice in test 18. The tests now run directly, `npx tsx addons/gaffer/gaffer.test.ts`, and `addons/gaffer/test-guard.ts` keeps a real `.env` from loading during them.
- **The board shows who built each job and how its rating held.** `start` takes `--builder standard|strong` and `--difficulty <1-5>` at the "go" and stamps the start date; `close` takes `--work-orders <n>`, `--report <dev report>` and `--difficulty held|off|not-valid`, the dev report's own figures, and stamps the close date. The job card adds Builder, Difficulty (the rating and its check), the work orders it took beside the estimate, the dates with the days they span, the footprint check ("missed 2: …" or "clean") and the dev report's path; the job list names the builder on jobs in progress and merged; the footer adds a tally (jobs per builder, swaps, checks held, off and not valid). `--builder` takes only the two labels, never a model or vendor name. A job restarted after a HALT on the other label gets a "builder swapped" note by itself and closes `not-valid`: the tool refuses any other check. Every field is optional, so an existing board renders as before until its next job passes them (`skills/f-board/SKILL.md`, `METHOD.md` §4 and §10).

Before a lesson becomes text, distill now tries the highest level that works: remove the wrong way, a type, a lint or script whose error names the fix, a test, and text last, for judgment calls. A product check becomes a job on the board (the foreman never writes product code), a method check a proposed Topping Out change, and each must be shown failing on the real past mistake from the card's evidence before the rule says `checked by <path>`. Until then the rule ends `(check owed: job <id>)`. Still only on the owner's word.
